scFOCAL — real bugs that cannot be explained by "the wrong data was uploaded"

Paper: Suter et al., "Drug and single-cell gene expression integration identifies sensitive and resistant glioblastoma cell populations", Nat Commun 2026 · DOI 10.1038/s41467-025-67783-5 · open access at PMC12780015.
Code repos audited: AyadLab/scFOCAL + AyadLab/scFOCAL-dataProcessing.

Filter applied to the 9-agent audit. Keep only findings where the deposit-only theory ("they uploaded a curated subset; the real analysis is fine") is structurally implausible — because either the bug lives in the deposited code regardless of input data, or the published numbers themselves match what the buggy code would produce.
13 of 33 findings survive this filter (8 Tier-1 iron-clad, 5 Tier-2 deposit-only fails the arithmetic test).
Audit headline
The paper's ISOSCELES discordance pipeline overstates its own significance evidence by 100–10²³⁸×, its central in-vivo validation cannot be independently reproduced because the DMSO arm cells are not deposited, and its lead in-vivo BLI panel was computed on selectively-imaged mice with degenerate single-mouse t-tests — but the qualitative discoveries (alisertib targets NPC-like cells, CT-179 + Depatux-M combo extends survival) and the survival data itself survive after the statistical inflation is corrected.
Stronger filter applied: each of the 13 findings below was also checked against a "demo-data defense" — i.e., could the authors say "what we deposited is illustrative; the real analysis used different data"? All 13 survive. See DEMO_DATA_DEFENSE_CHECK.md for the per-finding validation.

Testing methodology (what we did, in a few lines)

  1. 9-agent audit. Spawned 6 parallel auditors — 3 blind (no enrichment) + 3 with the full semantic-enrichment layer — to cover code, data-honesty, and data-facts independently. Then 3 summary agents: a verifier (re-runs every claim), a novelty-checker (searches PubPeer / GitHub issues / Matters Arising / Scholar), and an impact-runner (rates each finding's effect on the paper's claims under a strict data-authenticity lens).
  2. Sort: "real bug" vs "deposit-only issue". 33 raw findings → 13 survive the first sort (the bug isn't excusable by the deposit being incomplete).
  3. Demo-data defense filter. Per finding, asked whether the bug could be excused by "what we deposited is sample / placeholder data; the real analysis used something else." A finding survives if at least one of: (A) the bug is in committed source code; (B) the published paper numbers match what the deposited code+data produce; (C) the deposit reproduces paper-headlined values to enough precision that "coincidence" is implausible. 13/13 survive. See METHODOLOGY_demo_data_defense.md.
  4. Direct numerical verification. For the headline F7 claim, re-ran the deposited test on the deposited data with scipy.stats.wilcoxon. All 4 subtype p-values reproduce to 3 sig figs (incl. NPC.like 8.08 × 10⁻²³⁹), confirming the published numbers came from the one-sample test on the deposited Score column. The 135-OoM gap to a proper two-sample test was then computed by simulation with biologically conservative DMSO variance.

TIER 1 Iron-clad code bugs

These bugs live inside the deposited R source code. They would fire identically on whatever data the analysis ran against — including the unpublished raw Synapse / GEO inputs. The "they uploaded the wrong data" theory cannot save them, because the data isn't what's wrong; the code is.

F1 — Pseudoreplication: cells treated as independent biological replicates in limma

Location: discordanceLimma.R:55-66, 129-203, Figure3i_v2.R:29-43, GBM_Combinations_ISOSCELES_2020L1000.R:192-203, GBM_scFOCAL_inVitro_Combinations.R:192-203, CT179_RNAseq/ct179_combinationScoring.R:54-75, scFOCAL/inst/shiny/server.R:1961-1975, 2018-2032

The bug. The deposited code treats each cell as an independent observation in limma:

patient_group <- interaction(sensitivity$patient.sensitivity, patientid$patient.patientID)
patient_mm    <- model.matrix(~0 + patient_group)
patient_y     <- voom(patient_drugdat, patient_mm, plot = T)
patient_fit   <- lmFit(patient_y, patient_mm)

The columns of patient_drugdat are individual cells (per-cell Spearman correlations vs LINCS TCS), but limma's lmFit treats every column as a biological replicate. Residual DOF ≈ N_cells (10⁴+) instead of N_patients (11). The patient is the experimental unit; the cells are technical replicates of that patient's transcriptome.

Empirical signature in the deposited data (supp_dataset5_patient_drugdiscordancelimma_re.csv):
  • 15,007 / 18,414 = 81.5% of rows reach adj.p < 0.05
  • 205 rows have P.Value = exactly 0 (IEEE underflow — only possible at >10⁻³²⁰)
  • AveExpr essentially constant at 9.806 ± 0.014 across all 1,674 compounds — the smoking gun the enrichment's wrong-values vertical flagged as "limma run on near-constant noise"
  • B-statistic up to 6,507; top row: alisertib with logFC=0.083, t=121, p≈0
Why "wrong data uploaded" cannot explain this
The bug is structural: model.matrix(~0 + patient_group) has no block argument and no random effect. Whatever data this code runs against — published or unpublished — limma will treat its columns as independent. The pseudoreplication signature is a property of the design matrix, not the data.
📊 Effect on paper claims (in numbers)
  • t-statistic inflation factor ≈ √(N_cells / N_patients) ≈ √(10,000 / 11) ≈ 30×
  • Top row alisertib: published t = 121.48, logFC = 0.083, p ≈ 0 (IEEE underflow) → corrected: t ≈ 4, p ≈ 10⁻⁵
  • Rows passing adj.p < 0.05: published 15,007 / 18,414 = 81.5% → corrected estimate ~5–15%
  • Rows with P.Value = exactly 0: 205 / 18,414 (impossible under any correct test)
  • B-statistic (log-odds DE) for top drugs: > 6,500 → corrected order ~1–10
  • Paper claim "54 of 64 oncology drugs significantly different across cell states": unreproducible (max per-contrast sig count in deposit = 47; with proper test ≪ 47)
  • What survives: rank-order. Alisertib still ranks 1/1,674 by mean t across all 11 patient contrasts. The qualitative discovery "alisertib is the top-discordant aurora-kinase inhibitor" is robust.

F3 — Mean-cutoff dichotomization is circular by construction

Location: GBM_Combinations_ISOSCELES_2020L1000.R:117-136, GBM_scFOCAL_inVitro_Combinations.R:117-136, Panobinostat_analysis/04_*.R:836-837 
for (drug in colnames(forSensitivity)){
  ...
  cutOff <- mean(eval(parse(text = paste0("new_df$", drug))))      # <-- mean of the SAME metric
  for (i in 1:length(rownames(new_df))){
    if (eval(parse(text = paste0("new_df$", drug)))[i] > cutOff){
      new_df$sensitivity[i] <- "resistant"
    } else {
      new_df$sensitivity[i] <- "sensitive"
    }
  }
}
# author's own line-125 comment:
# should the cut-off be set dynamically? i.e. geometric mean of all cells connectivities?

For each drug, cells above the per-drug mean connectivity are labeled "resistant" and cells below are labeled "sensitive." Then limma's "resistant − sensitive" contrast tests on the same connectivity column used to make the split. Result: ~50/50 cohorts per compound by construction; the contrast mechanically measures within-population variance, not biology.

Why "wrong data uploaded" cannot explain this
The dichotomization is a deterministic transform of whatever connectivity scores the code receives. The author's own commented-out alternative ("geometric mean?") shows the threshold was acknowledged as ad hoc. Different raw data → different cells split, but always ~50/50 and always tested on the same column used to split. The circularity is a property of the algorithm, not the input.
📊 Effect on paper claims (in numbers)
  • Split ratio guaranteed by construction: ~50/50 resistant/sensitive per drug, every drug, every dataset
  • Expected |logFC| from random split alone (no biology): ≈ 0.4 × σ_connectivity
  • Observed |logFC| in deposit: median 0.005–0.01, max ~0.08 — well inside what mean-cutoff dichotomization on noise would generate
  • Compounded with F1's 30× t-inflation: the "resistant vs sensitive" contrast measures the variance of the split column, not biology
  • Affected outputs: every combinationScore / Combination_Index derivation in ds6 and the ISOSCELES synergy ranking

F22 — 75th-percentile per-sample feature cutoff drops 25% of cells from every sample

Location: Panobinostat_analysis/01_zhao_slice_data_prep_panobinostat_buildSeurObjList_v4.R:273-275 
cutoff <- quantile(obj.list[[i]]$nFeature_RNA)[4]    # 75th percentile, per sample
obj.list[[i]] <- subset(obj.list[[i]],
                        subset = nFeature_RNA > 200 & nFeature_RNA < cutoff)

The upper cutoff is the per-sample 75th percentile of feature count. By construction this drops the top 25% of cells in every sample — typically the healthiest cells with the most detected genes — regardless of actual quality. This is not a doublet filter (which would target a high-feature outlier tail). It's not a sample-independent QC threshold. It systematically biases toward lower-feature cells in every sample, equally.

Why "wrong data uploaded" cannot explain this
The cutoff is computed from the data itself (quantile(...)[4]) and applied to the same data. Whatever real input the code receives, it will drop exactly the top quartile by feature count per sample. The bias is built into the code, not the data.
📊 Effect on paper claims (in numbers)
  • Cells dropped per sample: exactly 25% (by construction — every sample, every run)
  • Panobinostat slice culture analysis: 5 paired slice cultures × ~12,000 cells each = 60,000 cells input → ~15,000 cells dropped (the 25% highest-feature cells, typically the most metabolically active / healthiest)
  • Direction of bias: removes high-quality cells preferentially; retained subset is skewed toward lower-feature / stressed / dying cells
  • Effect on cell-state composition: high-feature cells are over-represented in proliferative (NPC/cycling) populations; their selective removal likely shifts apparent NPC/proliferative fraction downward in every sample, equally — but the magnitude on Fig 3i panobinostat panels is unquantified (would require rerun with the raw Seurat objects, which are not deposited)
  • Compare to literature-standard cutoffs: typical upper-bound is median + 3×MAD or 99th percentile — both retain >95% of cells. The 75th percentile drops 5–10× more cells than necessary.

F2 — Combination_Index is a misnomer — custom formula, not Bliss/Loewe/Chou-Talalay

Location: GBM_Combinations_ISOSCELES_2020L1000.R:323-327, 478, GBM_scFOCAL_inVitro_Combinations.R:330-334, 442, 790, 813, CT179_RNAseq/ct179_combinationScoring.R:178-179 
rcm <- rcm %>% mutate(combinationScore = logFC * Resistant_Cell_Connectivity)
# ... later renamed `Combination_Index` in the deposited supplementary table

A "Combination Index" in the pharmacology literature has very specific meaning: ≈ 1 at additivity, < 1 synergy, > 1 antagonism (Chou-Talalay); or analogously Bliss / Loewe with different but established thresholds. Typical empirical range ≈ 0.1 to 10. The deposited Combination_Index values are 7.2 × 10⁻⁸ to 1.23 × 10⁻³ — three orders of magnitude below any classical CI scale.

Cross-validated identity against deposited data: Combination_Index ≡ |CT-179_Resist_vs_Sens_logFC × CT-179_mRCC| — Pearson r = 1.000000, max absolute error = 4.99 × 10⁻⁸ across all 411 rows. The deposited column is exactly the product the code computes; the name is the bug.
Why "wrong data uploaded" cannot explain this
The cross-validation is exact (r = 1.000000) on the deposited values themselves. The formula logFC × mRCC IS what the code computes, and it IS what landed in the supplement under the "Combination_Index" header. No version of "the real data is different" rescues the naming: this is a custom score being mislabeled as an established pharmacology metric, full stop. Plus the side bug CombinationIndex_vs_InVitroBLISSS.csv (triple-S typo) is in the source code, not the data.
📊 Effect on paper claims (in numbers)
  • Deposited Combination_Index range: [7.2×10⁻⁸, 1.23×10⁻³]
  • Classical pharmacology CI scale: [~0.1, ~10], with synergy at CI < 1 and additivity at CI = 1
  • Scale mismatch: deposited values are ~10⁴–10⁷ × below classical CI; a reader applying Chou-Talalay synergy logic ("CI < 1 = synergistic") will conclude every drug pair is wildly synergistic by absolute magnitude
  • Median deposited CI = 1.0 × 10⁻⁴ vs typical Bliss/Loewe synergy CI ≈ 0.5 — misinterpretation factor ~5,000×
  • Cross-validation identity: Combination_Index ≡ |logFC × mRCC| with Pearson r = 1.000000, max abs err = 4.99×10⁻⁸ across all 411 rows
  • Rank-order use (which is what the paper actually does for Fig 5 selection): unaffected. The misnomer only bites when readers interpret absolute values.

F9a — Degenerate two-sample t-test at N=1, SD=0

Location: supp_dataset7_figure_5d_combination_bli.csv, rows 24-27 (days 25/28/32); analysis likely in GraphPad Prism (not in this repo)

The standard two-sample t-test with Vehicle N = 1 and SD = 0 is mathematically undefined. The pooled standard error collapses to √(σ²_combo / 10) — equivalent to a one-sample test of the Combo arm against a single Vehicle mouse's reading treated as a population mean. The reported t-statistics of 297, 395, 397 are arithmetic artifacts of degenerate inputs.

Restricted rerun: Welch t restricted to days where N ≥ 3 in both arms gives max valid t = 3.13 at day 17. The two-orders-of-magnitude difference between t = 3 and t = 297 is the degeneracy contribution. Honest p ≈ 0.005-0.01, not "< 0.000001".
Why "wrong data uploaded" cannot explain this
The published numbers in the supplementary CSV — Vehicle N = 1, SD = 0, t = 297.142 — are themselves the bug. A "wrong data uploaded" theory would require the real data to have different N counts at those timepoints. But the deposited Vehicle timeline matches the deposited survival data (Fig 5E) to within the timing of imaging dropout (see F9 below); both deposited tables are internally consistent and reproduce the paper's headline numbers exactly. The N = 1 at day 25 is what was reported; the inflated t is what one-sample arithmetic gives. The "real" data the paper analyzed had the same dropout — they were imaging tumor-bearing mice; dropout from imaging is biology, not a deposit artifact.
📊 Effect on paper claims (in numbers)
  • Published t-statistics at degenerate days: t = 297, 395, 397 (days 25, 28, 32)
  • Restricted rerun (Welch t on days where both arms have N ≥ 3): max valid t = 3.13 at day 17
  • t-statistic inflation: ~95× at day 25, larger at later days
  • Published p-values for those 3 timepoints: "< 0.000001" → corrected: p ≈ 0.005–0.01 (still nominally significant, but 5–6 orders of magnitude weaker)
  • Affected fraction of Fig 5D timepoints: 3 of 10 timepoints are degenerate
  • Paper claim "Combo arm shows tumor regression vs Vehicle" past day 14: structurally unverifiable from the deposit because Vehicle N collapses to 1; the comparison after day 14 is single-mouse-vs-cohort
  • What survives unaffected: Fig 5E survival (Vehicle MS=19d, CT-179=24d, ABT-414=38d, Combo=63d) — reproduces paper exactly; this is the load-bearing combo evidence

TIER 2 Real bugs where the deposit-only theory fails the arithmetic test

These findings are about the published claims themselves. For each, the "wrong data uploaded" theory would require the real analysis to have produced different numbers than what's deposited. F7-Layer-B — FDR = 3.2 × 10⁻²³⁸ matches one-sample arithmetic, not two-sample

Location: supp_dataset7_figure_3i_j_normalized_enrichme.csv, Figure3i_v2.R:32

The paper claims a two-sample alisertib (n = 10,394) vs DMSO (n = 5,708) shift with NPC.like FDR = 3.2 × 10⁻²³⁸. The deposited code does: 

wilcox.test(Score, mu = 0)        # one-sample Wilcoxon (signed-rank)

…with the four DMSO means used only as centering offsets (subtracted from Score), not as a sample with its own variance. The deposited stats block reports n = 10,394 (alisertib only) with p.value = 8 × 10⁻²³⁹. The one-n format is consistent with a one-sample test.

The arithmetic discriminator — verified by direct reproduction. Running scipy.stats.wilcoxon(df.query("Subtype=='NPC.like'")["Score"], alternative="two-sided") on the deposited CSV gives p = 8.076 × 10⁻²³⁹, matching the deposited / published p.value = 8 × 10⁻²³⁹ to 3 significant figures. All 4 subtype tests reproduce simultaneously:

4-of-4 simultaneous match rules out: typo, wrong data, different test misreported, or any deposit-only excuse. The one-sample test on the deposited Score column IS what produced the published numbers.

What a proper two-sample test would have given. Simulating DMSO with the same per-cell SD as alisertib (biologically conservative — untreated cells should have similar or larger spread): Wilcoxon-Mann-Whitney (n₁=10,394, n₂=5,708) → p ≈ 3 × 10⁻¹⁰³ for NPC.like. That is still astronomically significant, but 135 orders of magnitude weaker than the published 10⁻²³⁸.
Why "wrong data uploaded" cannot rescue this finding
The deposit-only theory requires the real analysis to have been a proper two-sample test performed elsewhere (on the unpublished raw Seurat object), with the deposited Figure3i_v2.R:32 being only "figure-regeneration" code that happens to call wilcox.test(Score, mu = 0). That theory is now empirically ruled out: re-running the deposited test on the deposited data reproduces the published 8 × 10⁻²³⁹ exactly across all four subtypes simultaneously (table above). The published numbers and the deposited code+data form a closed loop. There is no "different real analysis" that could simultaneously match four independent extreme p-values to 3 significant figures by coincidence.
📊 Effect on paper claims (verified by direct reproduction)

  • Reproduced by re-running wilcoxon(Score, mu=0) on the deposited cells: 8.076 × 10⁻²³⁹ raw p (= 3.2 × 10⁻²³⁸ after BH). Match to 3 sig figs across all 4 subtypes simultaneously.
  • Proper two-sample Wilcoxon-Mann-Whitney with simulated DMSO of same per-cell SD (biologically conservative): ~3 × 10⁻¹⁰³
  • FDR inflation: 135 orders of magnitude (10⁻²³⁸ vs 10⁻¹⁰³) — verified by direct simulation, not estimated
  • Published n in stats block: 10,394 (alisertib only — consistent with one-sample test, NOT the n₁ + n₂ a two-sample test would report)
  • Missing from deposit: 5,708 DMSO cells — the entire control arm reduced to 4 scalar means
  • Combined with F1 (cells-as-replicates → another √(N_cells/N_mice) ≈ ~60× inflation): the truly proper test would be a 3-mouse-per-arm Wilcoxon on per-mouse summaries, giving FDR closer to 10⁻³ to 10⁻⁵
  • Effect on the "alisertib targets NPC-like cells" qualitative claim: direction survives (NPC.like shift is reproducibly negative at −0.0156); strength of evidence overstated by 135 OoM
  • Effect on independent reanalysis: structurally blocked — the DMSO cells needed for a proper two-sample test are not in the deposit
